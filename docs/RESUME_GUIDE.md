# SolarAI-X简历与面试指南

## 推荐项目名称

**SolarAI-X——基于MCP与RAG的太阳能领域智能分析Agent**

## 简历三条描述

- 基于DeepSeek与MCP构建太阳能领域智能分析Agent，将知识检索、硅电池参数仿真、钙钛矿老化/参数/带隙预测及曲线绘制封装为9个领域工具，实现模型动态发现工具、生成参数、执行调用并基于工具结果完成回答。
- 构建基于BGE Embedding的本地RAG流程，使用段落感知重叠切片、向量候选召回、词法覆盖重排序与重复片段过滤，保留来源文件和分块编号；通过FastAPI与SSE流式返回推理、工具结果和图像。
- 为工具循环增加MCP工具白名单、发现的JSON Schema参数校验、最大调用轮次和执行超时；只对只读检索工具执行有限重试，避免文件生成工具重复产生副作用，并通过脚本模型验证多轮调用、非法参数和断连边界。
- 编写基于现有手册的24题检索评测，固定开发/测试分组，对比原切片与重切片的来源命中、证据命中和无答案空检索；提供真实本地工具的离线演示与一键证据收集脚本。

## 技术栈

`Python / DeepSeek API / MCP / Tool Calling / RAG / BGE / FastAPI / Gradio / PyTorch / AutoGluon / SSE / pytest`

## 30秒介绍

SolarAI-X是一个面向太阳能和钙钛矿领域的智能分析Agent。它不是只让大模型回答问题，而是通过MCP向DeepSeek提供9个领域工具，包括知识检索、太阳能电池仿真、钙钛矿老化和带隙预测。模型根据用户问题选择工具、生成参数，Python执行后把数值和图表返回模型，再由模型生成最终解释。系统使用FastAPI提供流式接口，并用Gradio完成可视化展示。

## 面试时必须区分的内容

- 如果AutoGluon模型不是你亲自训练的，应说“集成并封装模型”，不要说“独立训练模型”；
- RAG使用BGE Embedding和本地PKL向量，不要声称使用了向量数据库；
- 对话历史当前是内存存储，不要声称已经实现数据库长期会话；
- MAPbIBr 当前为线性公式演示，未验证实验精度；三个缺少训练与验证资料的历史多项式模型已停用，不能将其历史指标写成已验证预测效果；
- MCP负责工具发现和执行协议，DeepSeek负责工具选择和自然语言回答。
- 当前离线验证运行的是关键词后端，没有运行BGE语义模型评测；脚本模型仅验证编排，不是模型自主决策成功率。
- 评测覆盖16份既有来源和2514个原片段，但问题集是作者根据手册编写的小样本，不能代表全部业务。

## 高频追问

### 为什么使用MCP，而不是在FastAPI里直接调用函数？

MCP把工具名称、描述、参数Schema和执行接口标准化。领域工具可以独立运行，也可以被不同模型客户端复用。FastAPI只负责会话、流式输出和协调，不需要硬编码每一个工具的调用方式。

### RAG的数据流是什么？

领域文档先按段落做带重叠分块，再通过BGE生成向量并保存来源映射。查询阶段先按向量相似度扩大候选集，再结合查询词覆盖率做二阶段重排序和去重；最终片段作为工具结果放回对话上下文，再由DeepSeek生成回答。

### 为什么副作用工具不自动重试？

网络超时并不代表服务端一定没有执行。仿真和绘图可能已经产生文件，如果直接重试会造成重复结果。因此当前只对`search_embedded_text`这类只读工具做有限指数退避重试，其他工具超时后记录错误并交给Agent或用户决定下一步。

### 模型目录缺失为什么服务还能启动？

维护版将模型加载从“强制启动条件”改成了“独立能力状态”。启动时记录各模型组是否加载成功，健康接口返回具体状态；只有调用缺失模型对应的功能时才返回503，因此聊天、带隙预测等其他模块不受影响。

### 项目最大的不足是什么？

当前对话只保存在内存中，RAG还是本地文件索引，AutoGluon模型制品需要单独配置。虽然已用脚本模型覆盖多轮工具编排和错误边界，但没有测真实模型选工具质量与MCP SSE端到端传输。关键词模式的跨语言检索也有明显局限。下一步应优先补真实语义检索对照和在线验收，再考虑数据库长期会话及部署。
